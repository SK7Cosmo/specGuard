# SG-03B Design decision register

At SG-03B, each entry was open and assigned to M3 (Plan and Design), and dependent implementation was sequenced after validation. SG-04R prospectively supersedes that collective sequencing rule. Recommended first choices, rationale and proposed defaults are now recorded in [ADR SG-04R implementation decisions](SG-04R-implementation-decisions.md); product-owner review and controlled evidence remain open. A failed or missing proof keeps only the affected capability disabled or fail-closed, while unrelated implementation may continue.

| Decision | Dependency and risk | M3 exit evidence |
|---|---|---|
| Local Git, Markdown, YAML and JUnit intake libraries and limits | Baseline pinning precedes indexing, execution and evidence mapping. Object or parser behavior could escape the selected snapshot, retrieve external resources or exhaust resources. | Pin a valid snapshot and verify exact spec digest, source locations and approved limits. Controlled samples demonstrate safe rejection of a missing commit, malformed required objects, out-of-scope paths, excessive input bytes or depth and disallowed XML constructs. Prior state and out-of-scope sentinels remain unchanged. |
| Two-stack index and analyzer implementation | Trace candidates, ghost findings and proposed evidence mappings depend on reliable source locations across Python/FastAPI and React/Next.js. | Index representative source and tests from both stacks without running application modules. Verify deterministic candidate and nonmatch cases on equivalent pinned inputs, stable locations, and mixed and unsupported coverage diagnostics. |
| Loopback authority and session implementation | Protected audit reads, mutations, approvals and exports depend on the browser trust boundary. | Select proof establishment, storage, expiry and invalidation settings. Demonstrate allowed local access and denial for disallowed Host or Origin, originless mutations, and missing, invalid, expired or revoked proof before disclosure or mutation. |
| Supported host platform, runner backend, provisioning and recovery | Approved execution requires verified disposable isolation, bounded execution and cleanup, including after partial setup. Evaluate Windows with WSL2/Docker as a candidate. | Select the supported platform and backend. In a controlled environment, demonstrate recorded wall-time, CPU, memory, process and output limits, non-privileged execution, blocked network, no host credentials or writable source mount, process-tree termination and verified teardown. Demonstrate execution blocking across restart after unverified teardown and resumption after documented recovery. |
| Provider transport, redaction and validation limits | The remote trace suggestion path depends on exact consent binding, deterministic fallback and safe handling of untrusted responses. | Select transport, endpoint validation, covered credential formats, timeout and byte limits. Controlled endpoints demonstrate exact approved bytes, no transmission of unapproved content, no redirect traffic, fail-closed redaction, and prior verdict retention for failed provider calls. |
| Evidence storage, revision history and export representation | Provenance, recovery, supersession, and audit reopening depend on the persistence model. | Specify storage and JSON versioning. Round-trip a pinned audit and diagnostics for all three coverage statuses. Demonstrate stable notice references, retained historic evidence, stale applicability tracking, and an idempotent retry after failed intake or execution. |
| Controlled fixture and integration design | The full P0 gate spans both framework stacks, local UI, evidence, and optional AI. P1 visual checks need their own controlled flow. | Select the implementation stack and fixture repositories, pinned commits and specs, synthetic inputs, harness identities and independent assertions. Trace every P0 case and MVP scenario to a reproducible check. Specify the P1 visual flow and reserve it for M7. |
| Secret-safe specification intake and source view | SG-R004 requires exact source retention for accepted specifications, while secret handling previously applied only to evidence and AI excerpts. Rejection creates a privacy boundary before persistence and before any source, log, cache, export, evidence or provider flow. | Validate detector scope and failure handling; prove rejected secret-bearing Markdown and YAML never cross any persistent or outbound boundary, safe diagnostics do not reveal values, accepted source is byte-exact, and source-view architecture preserves only accepted originals. At SG-03B, M4 intake/source-view was sequenced after this proof; under SG-04R, the capability stays disabled until the proof passes. |

The [SG-03B report](../../codex-evidence/review/SG-03B.md) distinguishes open technical blockers from work that has implementation complexity. The [milestone plan](../../PLANS.md) and [acceptance cases](../TEST_PLAN.md) govern progression.
