# ADR SG-04R — Preferred implementation decisions and proposed defaults

**Status:** Recommended implementation baseline for product-owner review. Numeric values are proposed defaults, not verified runtime settings.  
**Decision owner:** Product owner.  
**Date:** 2026-11-25 (Asia/Calcutta).  
**Scope:** Resolve first implementation choices using SG-04E candidates; preserve all requirements and SG-03D security policy.

## Proposed resource and parser limits

The initial defaults below bound expected MVP fixtures and reduce accidental resource exhaustion. They require D01/D06/D07/D09/D10 proof and review. They are not normative product requirements and must be recorded with their actual effective value when a runtime is eventually enabled.

| Input or operation | Proposed default | Selection basis |
|---|---:|---|
| Specification upload | 8 MiB per file; 16 MiB total per audit | Large enough for a requirement catalog plus source formatting, while bounding receive and scanner memory. |
| Git snapshot | 20,000 tree entries; 512 MiB total selected blob bytes; 16 MiB per blob; reject symlinks/submodules for traversal | Covers a small-to-medium application fixture; caps total work and single-file parser exposure. Larger repositories receive explicit scope diagnostics rather than unbounded indexing. |
| Markdown | 8 MiB; 100,000 lines; 20,000 headings | Reuses the specification byte cap and bounds heading/location indexing. |
| YAML | 8 MiB; 100,000 nodes; depth 32; reject aliases, custom tags, duplicate keys | Matches the specification cap while limiting deeply nested or alias-amplified structures. |
| JUnit XML | 16 MiB; depth 64; 100,000 testcases; DTD/entities forbidden | Allows multi-suite reports but bounds tree expansion and case materialization. |
| Python / TypeScript source | 2 MiB per file; 20,000 eligible files; 512 MiB aggregate source bytes | Excludes unusually large generated/vendor files by explicit unsupported-scope notice and keeps syntax-tree memory bounded. |
| Static analysis | 30 seconds per 1,000 files, 120 seconds per audit; worker memory 1 GiB | Gives ordinary fixtures room for parsing while preventing a large snapshot from consuming unbounded time or memory. |
| Provider response | 1 MiB body; timeouts per transport row above | Trace proposals are small structured payloads; a bounded body limits accidental or hostile provider output. |
| Runner | Per-attempt limits in runner row above; all values recorded in evidence | Keep one developer-approved test attempt bounded; actual values must be measured and recorded by the isolated backend. |

For any exceeded bound, fail the affected operation without activating partial results; preserve prior audit state and emit a sanitized, specific limit reason. Candidate settings are tunable only through versioned policy and regression evidence.

## Decisions requiring further product-owner approval

The following proposed defaults affect host trust, user authority, data durability, or external transmission and need explicit review before the relevant capability is activated: bootstrap code and cookie lifetime/restart policy; SQLite and artifact layout; exact parser/version pins and numeric bounds; supported Python/TypeScript framework subset; secret-class patterns; fixed provider identity/endpoint, credentials and availability; Linux VM provider/host, image distribution and resource limits. Product-owner disposition does not replace the D01–D11 controlled evidence.

## Not verified in SG-04R

No package was installed, no runtime setting was configured, no database/server/browser/provider/runner was launched, no virtualization capability or permission was probed, and no external provider was contacted. All listed technologies and numbers are proposed choices only until a later task records actual versions, settings, and designated observations.
