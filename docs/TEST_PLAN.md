# SpecGuard test plan

## Strategy and fixture

These are planned product checks. The [requirements catalog](REQUIREMENTS.yaml) defines the expected behaviors. The [verification policy](VERIFICATION_POLICY.md) determines admissibility and verdicts. Each case below uses its linked criterion ID as the test case ID. Define the test oracle from the specification before inspecting the implementation. Use test-first development for intake, verdict rules, isolation and consent.

Use a controlled P0 Git fixture with a small FastAPI service, a React/Next.js UI, and its original Markdown and equivalent YAML specifications. Pin the commit and spec digest and add a second commit and specification revision for baseline changes. Include functioning examples alongside each seeded defect. Use synthetic records and credentials, a pinned runner environment, deterministic JUnit inputs, and controlled provider endpoints that capture requests. Fixture code and numeric limits are M3 decisions.

For each criterion case, retain the case ID, fixture commit and spec digest, method, expected and actual observations, result, and supporting artifact reference. For static cases retain rule configuration and matching or nonmatching paths. For manual cases retain reproducible steps, reviewer and observation. For automated cases retain the command or harness identity, result, and sanitized output. Record skipped and blocked cases with their causes.

## Exit criteria

Documentation validation checks catalog integrity, source references, dependency order, and the one-to-one mapping of all 68 criteria to cases by ID, priority, method and expected outcome. MVP verification requires passing evidence for all 53 P0 cases and all five MVP scenarios. A seeded failure passes its SpecGuard acceptance case when the product records the expected failed or unresolved outcome. Record the 12 P1 and three P2 cases against their respective gates. Review failure reports and retain their actual outcomes with the relevant baseline.
